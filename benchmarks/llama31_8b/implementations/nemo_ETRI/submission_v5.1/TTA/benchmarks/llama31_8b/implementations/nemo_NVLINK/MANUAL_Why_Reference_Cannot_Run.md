## 1. 한 문장 요약

> **레퍼런스는 "288대 서버 × 8개 GPU = 2,304개 GPU로 405B 모델을 돌리는 코드"이기 때문에,
> 우리의 "1대 서버 × 2개 GPU로 8B 모델을 돌리는 환경"에서는 코드 수준에서 실행 자체가 불가능합니다.**

비유하면, **대형 화물선 운항 매뉴얼로 소형 보트를 조종하려는 것**과 같습니다.
엔진 수, 조타 방식, 항로 설계가 근본적으로 다릅니다.

## 3. 원인 1: SLURM 원격 실행 강제 — 로컬 실행 불가

### 무엇이 문제인가?

레퍼런스의 메인 스크립트(`pretrain_llama31.py`)는 **반드시 SSH를 통해 원격 SLURM 클러스터에 작업을 제출**하도록 만들어져 있습니다. 로컬에서 직접 `python pretrain_llama31.py`를 실행하는 것이 **구조적으로 불가능**합니다.

### 코드에서의 증거

**`pretrain_llama31.py` 39~44행:**
```python
def slurm_executor(user, host, remote_job_dir, account, partition, ...):
    if not (user and host and remote_job_dir and account and partition ...):
        raise RuntimeError(
            "Please set user, host, remote_job_dir, account, partition, ..."
        )
```

→ `user`, `host`, `account`, `partition`이 모두 **필수 값**입니다.
하나라도 비어 있으면 즉시 에러로 종료합니다.

**`pretrain_llama31.py` 65~79행:**
```python
executor = run.SlurmExecutor(
    account=account,
    partition=partition,
    tunnel=run.SSHTunnel(       # ← SSH 터널 필수!
        user=user,
        host=host,
        job_dir=remote_job_dir,
    ),
    nodes=nodes,
    gres="gpu:8",               # ← GPU 8개 하드코딩!
    packager=run.GitArchivePackager(subpath="large_language_model_pretraining/nemo"),
)
```

### 비유로 이해하기

```
레퍼런스의 실행 구조:

  사용자 PC  ──SSH──►  원격 클러스터  ──SLURM──►  288개 노드에서 학습
     │                    │                           │
     └─ "여기서 명령만"    └─ "여기서 관리"              └─ "여기서 실제 실행"

우리 환경:

  서버 1대에서 직접 실행 (sbatch run.sub)
     │
     └─ 명령, 관리, 실행 모두 여기서
```

레퍼런스는 "3단 구조(PC→클러스터→노드)"이고, 우리는 "1단 구조(서버에서 직접)"입니다.
레퍼런스의 3단 구조를 우회할 방법이 코드에 없습니다.

### 이걸 고치려면?

`pretrain_llama31.py`의 SLURM 실행기 전체를 로컬 실행기로 **완전히 재작성**해야 합니다.
NeMo-Run의 `SlurmExecutor` → `LocalExecutor` 또는 직접 `torchrun` 호출로 변경이 필요합니다.

## 4. 원인 2: 405B 모델 전용 — 2개 GPU에 절대 안 들어감

### 무엇이 문제인가?

레퍼런스의 기본 대상은 **LLaMA 3.1 405B** 모델입니다.
이 모델은 파라미터만 해도 **810GB** (BF16 기준)이므로,
93GB GPU 2개(총 186GB)에 **물리적으로 들어가지 않습니다.**

### 메모리 계산

```
405B 모델의 메모리 요구량:

파라미터 저장:      405B × 2바이트(BF16)   = 810 GB
옵티마이저 상태:    405B × 8바이트(FP32×2)  = 3,240 GB
기울기:            405B × 2바이트          = 810 GB
활성화 값:         (레이어 126개, 시퀀스 8192) ≈ 수백 GB
─────────────────────────────────────────────────
총 필요:           약 5,000+ GB (5 TB 이상)

우리 GPU:          2 × 93 GB = 186 GB
부족분:            약 4,814 GB (26배 부족!)
```

### 코드에서의 증거

**`config.sh` 72행:**
```bash
export SIZE="405b"    # ← 기본값이 405B
```

**`pretrain_llama31.py` 286행:**
```python
parser.add_argument("--size", type=str, default="405b", ...)
```

### 비유

```
405B 모델을 2개 GPU에 넣는 것은:
  100톤 화물을 5톤 트럭에 싣는 것과 같습니다.
  20대의 트럭이 필요한데 2대밖에 없습니다.
```

## 5. 원인 3: 2,304개 GPU 병렬화 — 2개 GPU로는 구조적 불가능

### 무엇이 문제인가?

레퍼런스는 405B 모델을 2,304개 GPU에 분산하기 위해
**4가지 병렬화를 동시에 사용**합니다.
이 중 대부분은 GPU가 2개일 때 **수학적으로 불가능**합니다.

### 레퍼런스의 병렬화 설정

```
Tensor Parallel (TP)    = 8    → 행렬을 8개 GPU에 분할
Pipeline Parallel (PP)  = 7    → 126 레이어를 7단계로 분할 (각 18 레이어)
Virtual Pipeline (VP)   = 7    → 파이프라인 내 인터리빙
Context Parallel (CP)   = 2    → 시퀀스를 2개로 분할
Data Parallel (DP)      = 2304 ÷ (8×7×2) ≈ 20

총 GPU = TP × PP × CP × DP = 8 × 7 × 2 × 20 ≈ 2,240 (+ 여유분)
```

### 왜 2개 GPU로 안 되는가?

```
필요한 최소 GPU 수:

TP=8:   최소 8개 GPU 필요 (행렬을 8등분)
         → 우리: 2개 ❌  (4분의 1도 안 됨)

PP=7:   최소 7개 GPU 필요 (파이프라인 7단계)
         → 우리: 2개 ❌  (3분의 1도 안 됨)

VP=7:   PP=7이 전제조건
         → PP가 안 되니 VP도 불가 ❌

CP=2:   최소 2개 GPU 필요
         → 우리: 2개 ✅  (가능하지만 TP, PP에 먹힘)

TP × PP × CP = 8 × 7 × 2 = 112개 GPU가 최소 필요
우리는 2개뿐 → 56분의 1
```

### 코드에서의 증거

**`pretrain_llama31.py` 148행:**
```python
pretrain.trainer.strategy.virtual_pipeline_model_parallel_size = 7  # ← VP=7 하드코딩
```

**`pretrain_llama31.py` 78행:**
```python
gres="gpu:8",  # ← 노드당 GPU 8개 하드코딩
```

### 비유

```
405B 병렬화 = 112명이 동시에 하는 릴레이 달리기
  - 8명이 한 줄로 바통 터치 (TP)
  - 7줄이 순서대로 달림 (PP)
  - 2개 트랙에서 동시 진행 (CP)

우리 환경 = 2명으로 같은 릴레이를 하라는 것
  → 구조적으로 불가능
```

## 6. 원인 4: NVLink + InfiniBand 전용 최적화

### 무엇이 문제인가?

레퍼런스의 통신 최적화는 **NVLink(GPU 간 900GB/s)**와 **InfiniBand(노드 간 200Gb/s)**를 전제로 설계되었습니다. 우리 환경의 **PCIe Gen5(128GB/s)**에서는 이 최적화들이 동작하지 않거나 오히려 성능을 떨어뜨립니다.

### 속도 차이

```
통신 속도 비교:

NVLink (레퍼런스):     900 GB/s   ████████████████████████████████████████████░  100%
InfiniBand (레퍼런스):  25 GB/s   █░                                             2.8%
PCIe Gen5 (우리):      128 GB/s   ██████░                                       14.2%

→ 우리 환경은 NVLink의 14%에 불과한 대역폭
```

### 코드에서의 증거

**`pretrain_llama31.py` 164~177행:**
```python
# 405B 전용 통신 오버랩 설정
from nemo.collections.llm.recipes.tp_overlap_configs.userbuffers import (
    userbuffers_bf16_h100_h16384_tp8_cp2_mbs1_seqlen8192,  # ← H100 NVLink 전용!
)

pretrain.trainer.callbacks.append(
    run.Config(
        MegatronCommOverlapCallback,
        tp_comm_overlap=True,                    # ← NVLink 전제
        tp_comm_overlap_cfg=userbuffers_...,     # ← TP=8 전용 버퍼 설정
        defer_embedding_wgrad_compute=True,
    )
)
```

이 코드의 이름을 해석하면:
- `userbuffers`: GPU 간 공유 메모리 버퍼 (NVLink로만 고속 접근)
- `h100`: H100 GPU 전용
- `h16384`: 히든 크기 16384 (405B 모델)
- `tp8`: Tensor Parallel 8 (8개 GPU)
- `cp2`: Context Parallel 2

우리 환경(TP=2, 히든 크기 4096, PCIe)에 해당하는 설정은 **존재하지 않습니다.**

### 영향

```
PCIe 환경에서 NVLink 최적화를 적용하면:

1. 통신 오버랩이 오히려 느려짐
   → NVLink에서는 통신과 연산이 동시 진행 가능
   → PCIe에서는 대역폭이 부족해서 오버랩 효과 없음

2. 버퍼 크기 불일치
   → NVLink용 대용량 버퍼가 PCIe에서 메모리만 낭비

3. NCCL 알고리즘 불일치
   → NVLink는 Ring/Tree AllReduce 최적
   → PCIe는 더 단순한 알고리즘이 효율적
```

## 7. 원인 5: 8B 모델은 "디버깅용" — 수렴 검증 안 됨

### 무엇이 문제인가?

레퍼런스에서 8B 모델은 **"디버깅 전용"**으로 표시되어 있습니다.
공식 벤치마크는 오직 405B만 대상이며, 8B로 `log_ppl ≤ 3.3`에 수렴하는 것은 **검증된 적이 없습니다.**

### 코드에서의 증거

**`pretrain_llama31.py` 106~107행:**
```python
# Providing 8B and 70B here for debugging purpose
# Actual benchmark should use 405B
```

번역: "8B와 70B는 디버깅 목적으로만 제공합니다. 실제 벤치마크는 405B를 사용해야 합니다."

### 8B와 405B의 차이점 (레퍼런스 코드 기준)

| 항목 | 405B (공식) | 8B (디버깅용) | 문제 |
|------|------------|-------------|------|
| 목표 log_ppl | 5.6 | 3.3 (별도 규정) | 레퍼런스에 3.3 목표 코드 없음 |
| 학습률 | GBS 기반 자동 계산 | 하드코딩 3e-4 | 최적화 안 됨 |
| Warmup 스텝 | 8000 × ceil(1152/GBS) | 동일 공식 적용 | GBS 작으면 엄청 길어짐 |
| 검증 빈도 | 18,432 시퀀스마다 | 동일 | GBS 작으면 매우 자주 검증 |
| 통신 오버랩 | 적용 | 미적용 | 성능 최적화 없음 |
| 파이프라인 | VP=7 | 없음 | 구조 다름 |

### 실제 영향

레퍼런스의 8B 설정으로 학습하면:
- 수렴까지의 하이퍼파라미터가 **튜닝되지 않음**
- 검증 빈도가 **비효율적** (너무 자주 또는 너무 드물게)
- 학습률 스케줄이 **GBS 차이를 고려하지 않음**
- **수렴 가능 여부 자체가 불확실**

## 8. 원인 6: 배치 사이즈 1,152 — 2개 GPU로 처리 불가

### 무엇이 문제인가?

레퍼런스의 기본 Global Batch Size(GBS)는 **1,152**입니다.
이는 2,304개 GPU에서 각 GPU가 조금씩 나눠 처리하도록 설계된 것입니다.

### 메모리 계산

```
GBS=1,152를 2개 GPU에서 처리하려면:

GPU당 처리량 = 1,152 ÷ 2 = 576 시퀀스
시퀀스당 메모리 (8B 모델):
  활성화 값 ≈ 시퀀스길이(8192) × 히든(4096) × 레이어(32) × 2바이트
           ≈ 약 2 GB/시퀀스

576 시퀀스 × 2 GB = 약 1,152 GB
→ GPU 메모리 93GB의 12배!

물론 Gradient Accumulation으로 나눌 수 있지만:
  GA = 576 / MBS(1) = 576회 반복
  → 한 스텝에 Forward+Backward를 576번 반복
  → 스텝 시간: 576 × 6초 ≈ 57분/스텝
  → 20,000 스텝 × 57분 = 19,000시간 ≈ 2.2년
```

### 코드에서의 증거

**`config.sh` 72행:**
```bash
export GBS=1152
```

**`pretrain_llama31.py` 295행:**
```python
parser.add_argument("--gbs", type=int, default=1152)
```

### 비유

```
GBS=1,152는:
  "한 번에 1,152명분의 급식을 만들어라"와 같습니다.

  2,304개 GPU = 2,304명의 요리사가 나눠서 처리 → 각 0.5명분 (쉬움)
  2개 GPU     = 2명의 요리사가 처리 → 각 576명분 (불가능!)
```

## 9. 원인 7: MLPerf 로깅이 405B로 하드코딩

### 무엇이 문제인가?

MLPerf 벤치마크는 **정확한 벤치마크명, 플랫폼명, 목표값**을 로그에 기록해야 합니다.
레퍼런스 코드에 이 값들이 **405B 전용으로 하드코딩**되어 있습니다.

### 코드에서의 증거

**`callbacks.py` 36행:**

## 11. 원인 9: 학습 시간 계산 — 수백만 시간 필요

### 405B 모델의 학습 시간 (레퍼런스 기본 설정)

```
레퍼런스 (2,304 GPU, 405B):
  GBS = 1,152
  최대 스텝 = 1,200,000
  스텝 시간 ≈ 약 20~30초 (추정, 2304 GPU)
  총 시간 ≈ 1,200,000 × 25초 ≈ 347일 ≈ ~1년

  → 2,304 GPU로도 수개월~1년 소요
```

### 만약 우리 환경 (2 GPU)에서 405B를 돌린다면?

```
(물리적으로 불가능하지만, 가정해보면)

GPU 성능 비율: 2 / 2,304 = 0.00087 (0.087%)
소요 시간: 347일 / 0.00087 ≈ 400,000일 ≈ 1,096년

→ 약 1,100년이 필요합니다.
```

### 8B 모델로 바꿔도?

```
레퍼런스의 8B 설정 (GBS=1,152 유지):
  최대 스텝 = 1,200,000
  GA = 1,152 / 2 = 576 (MBS=1 기준)
  스텝 시간 ≈ 576 × 6초 ≈ 57분
  총 시간 ≈ 1,200,000 × 57분 ≈ 1,300년

GBS를 8로 줄이면:
  최대 스텝 = 1,200,000 × (1,152/8) = 172,800,000 스텝
  스텝 시간 ≈ 5.9초
  총 시간 ≈ 172,800,000 × 5.9초 ≈ 32년

→ GBS를 줄여도 32년이 걸립니다.
  (Dell 구현체는 약 20,000 스텝, 38시간에 완료)
```

### 왜 이렇게 차이가 나는가?

```
레퍼런스:  "1,200,000스텝을 하면 언젠가 수렴합니다" (보수적)
Dell:     "20,000스텝이면 충분합니다" (8B에 최적화된 설정)

레퍼런스의 스텝 수 공식: max_steps = 1,200,000 × ceil(1152 / GBS)
Dell의 실제 수렴 스텝:   약 20,352 스텝

→ 레퍼런스는 405B 기준으로 스텝 수를 계산하므로
  8B에는 터무니없이 과도한 스텝 수가 됩니다.
```

## 12. 원인 10: 체크포인트 크기 — 5.2TB

### 코드에서의 증거

**`config.sh` 59행의 주석:**
```bash
# Notice that this path must be able to hold at least 5.2TB data
# since each checkpoint is 5.2TB.
export CONTINUAL_CKPT=""
```

### 크기 비교

```
405B 체크포인트: 5.2 TB (1개)
  → 파라미터: 405B × 2바이트 = 810 GB
  → 옵티마이저: 405B × 8바이트 = 3,240 GB
  → 기타 메타데이터: ~1,150 GB

8B 체크포인트: 약 48 GB (1개)
  → 파라미터: 8B × 2바이트 = 16 GB
  → 옵티마이저: 8B × 8바이트 = 32 GB

차이: 약 108배
```

405B 체크포인트를 저장하려면 **5.2TB 이상의 고속 스토리지**가 필요합니다.
일반 서버 환경에서는 이 정도 스토리지를 확보하기 어렵습니다.

## 13. 데모 모드는 되지 않을까?

### 데모 설정 분석

**`demo_config.sh`:**
```bash
export NNODES=1            # ✅ 1노드 (우리와 같음)
export GPUS_PER_NODE=1     # ⚠️ 1 GPU (우리는 2개)
export SIZE="8b"           # ✅ 8B 모델 (우리와 같음)
export GBS=16              # ⚠️ GBS 16 (우리는 8)
export MBS=1               # ✅ 동일
export MAX_STEPS="100"     # ❌ 100스텝만 (수렴 불가)
export SEEDS="42"          # ✅ 고정 시드
```

### 데모 모드의 한계

```
1. NeMo-Run + SSH 의존성은 여전함
   → slurm_executor()가 여전히 필수
   → "USER=root, HOST=localhost"로 설정해도
     SLURM 데몬이 필요

2. 100스텝으로는 수렴 불가
   → 8B 모델은 ~20,000스텝 필요
   → 100스텝은 스모크 테스트용

3. GPU 1개 전제
   → TP=1, DP=1로 설정됨
   → 우리의 2 GPU를 활용하려면 수정 필요

4. 데이터 경로 다름
   → 데모용 축소 데이터셋 사용
   → 실제 C4 전체 데이터와 경로 불일치
```

### 결론: 데모 모드도 직접 실행 불가

데모 모드도 NeMo-Run + SLURM 의존성을 우회할 수 없으므로,
우리 환경에서 **그대로 실행하는 것은 불가능**합니다.

### Dell이 레퍼런스에서 바꾼 것들

레퍼런스를 우리 같은 환경에서 실행하려면 **거의 완전히 재작성**해야 합니다.

```

│ 실행 시스템            │ NeMo-Run + SSH → SLURM 직접 (run.sub)    │

│ 워밍업                │ 없음 → 합성 데이터 2스텝 워밍업             │
│ 정밀도                │ BF16만 → BF16/FP8/FP4 선택 가능            │
│ 최적화                │ 기본 → CUDA Graph, NCCL 튜닝, TE 등       │
│ 검증 주기             │ 18,432 시퀀스 고정 → 환경변수로 설정 가능   │
│ 목표 log_ppl          │ 5.6 하드코딩 → 3.3 (환경변수)              │
│ MLPerf 로깅           │ 405B 하드코딩 → 8B/405B 자동 선택          │
│ 컨테이너              │ NeMo 24.12 → PyTorch 25.09 기반 커스텀     │
│ 소프트웨어            │ 기본 버전 → 최신 버전 + H100 전용 빌드      │

│ 컨테이너 환경변수      │ 자동 → --container-env 명시적 전달          │
└──────────────────────┴───────────────────────────────────────────┘
```

### 비유

```
레퍼런스 → Dell 구현체는:

"대형 여객기 설계도" → "경비행기 제작"과 같습니다.

같은 "비행기"라는 개념을 공유하지만:
- 엔진 수가 다르고 (2,304 → 2)
- 활주로 길이가 다르고 (288노드 → 1노드)
- 승객 수가 다르고 (GBS 1,152 → 8)
- 조종 방식이 다릅니다 (NeMo-Run → SLURM 직접)

기본 물리 법칙(Transformer, AdamW, 경사하강법)은 같지만,
구현의 거의 모든 부분이 다릅니다.
```
