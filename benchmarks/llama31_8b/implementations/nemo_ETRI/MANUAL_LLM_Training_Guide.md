## 1. 큰 그림: LLM 학습이란?

### 비유로 이해하기

LLM(Large Language Model) 학습은 **"아이에게 언어를 가르치는 것"** 과 비슷합니다.

```
[ 엄청나게 많은 텍스트 ]  →  [ 모델 (학생) ]  →  [ 다음 단어를 잘 예측하는 능력 ]
     (교과서)                  (8B개의 뉴런)           (졸업 기준: log_ppl ≤ 3.3)
```

- **교과서**: C4 데이터셋 (인터넷 텍스트 약 15억 개 샘플)
- **학생**: LLaMA 3.1 8B 모델 (80억 개의 조절 가능한 숫자 = 파라미터)
- **수업 방식**: "이 문장에서 다음 단어가 뭘까?" 를 반복해서 맞추게 하기
- **졸업 기준**: 검증 시험에서 log perplexity ≤ 3.3 달성

### 학습의 한 스텝은 이렇게 진행됩니다

```
┌──────────────────────────────────────────────────────────────┐
│                        한 스텝 (약 5.9초)                      │
│                                                              │
│  1. 데이터 읽기: 텍스트 8개 묶음을 GPU에 올림                     │
│         ↓                                                    │
│  2. Forward Pass: 모델이 다음 단어를 예측                       │
│         ↓                                                    │
│  3. Loss 계산: 예측이 얼마나 틀렸는지 숫자로 측정                  │
│         ↓                                                    │
│  4. Backward Pass: 어떤 파라미터가 틀린 원인인지 역추적             │
│         ↓                                                    │
│  5. 파라미터 업데이트: 틀린 방향의 반대로 파라미터 수정              │
│         ↓                                                    │
│  → 이것을 약 20,000~25,000번 반복하면 모델이 언어를 배움           │
└──────────────────────────────────────────────────────────────┘
```

### 우리의 목표

MLPerf Training 벤치마크에서 정해진 규칙 안에서 **가능한 한 빨리** 모델을 졸업시키는 것입니다.

- 졸업 기준: 검증 데이터에서 `log_ppl ≤ 3.3`
- 규칙: 하이퍼파라미터는 바꿀 수 있지만, 모델 구조와 데이터는 고정
- 측정: `run_start` ~ `run_stop` 사이의 시간

## 2. 하드웨어 환경 이해하기

### 현재 시스템 사양

```
┌─────────────────────────────────────────────────┐
│              서버 1대 (1 Node)                    │
│                                                  │
│   ┌──────────────┐    ┌──────────────┐          │
│   │   GPU 0       │    │   GPU 1       │          │
│   │  H100 NVL     │◄──►│  H100 NVL     │          │
│   │  95,830 MiB   │PCIe│  95,830 MiB   │          │
│   │  (~93 GB)     │    │  (~93 GB)     │          │
│   └──────────────┘    └──────────────┘          │
│         ▲                    ▲                    │
│         │      PCIe Gen5     │                    │
│         └────────┬───────────┘                    │
│                  │                                │
│         ┌────────▼────────┐                      │
│         │     CPU + RAM    │                      │
│         │   데이터 로딩     │                      │
│         └─────────────────┘                      │
│                                                  │
│   CUDA 13.0 / Driver 580.82.07                   │
└─────────────────────────────────────────────────┘
```

### GPU 메모리는 어떻게 사용되나?

GPU 93GB 메모리의 사용 내역을 비유하면:

```
93GB GPU 메모리 = 93칸짜리 책장

┌────────────────────────────────────────────────────────────┐
│ 모델 파라미터 (약 16GB)                                      │
│ → 80억 개 숫자를 BF16(2바이트)로 저장 = 8B × 2 = ~16GB       │
├────────────────────────────────────────────────────────────┤
│ 옵티마이저 상태 (약 32GB)                                    │
│ → AdamW는 파라미터당 추가 숫자 2개를 FP32로 저장               │
│ → 모멘텀(m) + 분산(v) = 8B × 4바이트 × 2 = ~64GB            │
│ → 분산 옵티마이저로 2GPU에 나누면 = ~32GB/GPU                 │
├────────────────────────────────────────────────────────────┤
│ 기울기 (약 16GB)                                            │
│ → 각 파라미터의 수정 방향 = 8B × 2바이트 = ~16GB              │
├────────────────────────────────────────────────────────────┤
│ 활성화 값 (약 20-25GB)                                      │
│ → Forward Pass 중간 계산 결과, Backward에서 재사용             │
│ → 시퀀스 길이 8192 × 히든 크기 4096 × 레이어 수 32            │
├────────────────────────────────────────────────────────────┤
│ 임시 버퍼 + NCCL 통신 + 기타 (약 3-5GB)                      │
│ → GPU 간 통신 버퍼, 연산 임시 공간                             │
├────────────────────────────────────────────────────────────┤
│ 여유 공간 (약 1-3GB) ← 여기가 매우 빠듯!                      │
└────────────────────────────────────────────────────────────┘
```

**핵심 포인트**: 93GB가 거의 꽉 차 있어서 새로운 기능(예: Transformer Engine)을 켜면
추가 메모리 1-2GB만으로도 OOM(Out Of Memory, 메모리 부족) 에러가 발생합니다.

### PCIe vs NVLink: GPU 간 통신 속도

```
NVLink (데이터센터용):  ~900 GB/s  (고속도로)
PCIe Gen5 (우리 환경):  ~128 GB/s  (일반 도로)
```

우리 환경은 PCIe 연결이라 GPU 간 데이터 전송이 상대적으로 느립니다.
따라서 GPU 간 통신을 최소화하는 것이 성능의 핵심입니다.

## 3. 소프트웨어 스택: 레고 블록처럼 쌓인 구조

학습 시스템은 여러 소프트웨어가 층층이 쌓여 동작합니다:

```
┌──────────────────────────────────────────────┐
│          우리가 수정하는 설정 파일                │  ← config_PCIeH100_TTA.sh
├──────────────────────────────────────────────┤
│              pretrain.py                      │  ← 학습 스크립트 (진입점)
├──────────────────────────────────────────────┤
│         NeMo 2.0 Framework                   │  ← 학습 오케스트레이션
├──────────────────────────────────────────────┤
│         Megatron-Core                        │  ← 대규모 모델 병렬 처리
├──────────────────────────────────────────────┤
│     Transformer Engine (TE)                  │  ← 커널 최적화, FP8 지원
├──────────────────────────────────────────────┤
│           PyTorch                            │  ← 딥러닝 프레임워크
├──────────────────────────────────────────────┤
│        NCCL (통신 라이브러리)                   │  ← GPU 간 데이터 교환
├──────────────────────────────────────────────┤
│      CUDA / cuDNN / cuBLAS                   │  ← GPU 연산 라이브러리
├──────────────────────────────────────────────┤
│        NVIDIA H100 GPU                       │  ← 하드웨어
└──────────────────────────────────────────────┘
```

### 각 층의 역할

| 계층 | 역할 | 비유 |
|------|------|------|
| **config 파일** | 학습 설정값 정의 | 요리 레시피 |
| **pretrain.py** | 학습 전체 흐름 제어 | 주방장 |
| **NeMo** | 데이터, 모델, 학습 루프 관리 | 주방 매니저 |
| **Megatron-Core** | 모델을 여러 GPU에 분산 | 일을 나눠주는 팀장 |
| **Transformer Engine** | 연산을 합쳐서 빠르게(fused kernel) | 효율적인 조리 도구 |
| **PyTorch** | 텐서 연산, 자동 미분 | 기본 조리 도구 |
| **NCCL** | GPU 간 통신 | 주방 간 식재료 전달 |
| **CUDA/cuDNN** | GPU 하드웨어 직접 제어 | 가스레인지, 오븐 |

## 4. 모델 구조: LLaMA 3.1 8B의 내부

### Transformer 아키텍처

LLaMA 3.1 8B는 **Transformer** 라는 구조를 사용합니다.
핵심 아이디어는 "문장의 모든 단어가 다른 모든 단어를 참고한다" 입니다.

```
입력: "오늘 날씨가 정말"  →  다음 단어 예측: "좋다" (확률 35%), "덥다" (확률 20%) ...

┌─────────────────────────────────────────────┐
│              LLaMA 3.1 8B                    │
│                                              │
│  ┌─────────────────────────────────────┐    │
│  │  Embedding Layer                     │    │  토큰 → 숫자 벡터 변환
│  │  (128,256 단어 × 4,096 차원)         │    │
│  └──────────────┬──────────────────────┘    │
│                 │                            │
│                 ▼                            │
│  ┌─────────────────────────────────────┐    │
│  │  Transformer Block × 32층            │    │  핵심 연산 블록
│  │  ┌──────────────────────────────┐   │    │
│  │  │  Self-Attention               │   │    │  "어떤 단어를 주목할까?"
│  │  │  (32 heads, 128 dim/head)    │   │    │
│  │  ├──────────────────────────────┤   │    │
│  │  │  Feed-Forward Network (FFN)   │   │    │  "정보를 변환하자"
│  │  │  (4096 → 14336 → 4096)       │   │    │  SiLU 활성화 + GLU
│  │  ├──────────────────────────────┤   │    │
│  │  │  RMSNorm (정규화)             │   │    │  "값이 너무 커지지 않게"
│  │  └──────────────────────────────┘   │    │
│  │         × 32번 반복                  │    │
│  └──────────────┬──────────────────────┘    │
│                 │                            │
│                 ▼                            │
│  ┌─────────────────────────────────────┐    │
│  │  Output Layer (LM Head)              │    │  벡터 → 다음 단어 확률
│  │  (4,096 → 128,256)                  │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### 핵심 숫자들

| 항목 | 값 | 의미 |
|------|-----|------|
| 파라미터 수 | 80억 개 (8B) | 모델이 조절하는 숫자의 개수 |
| 레이어 수 | 32 | Transformer 블록 반복 횟수 |
| 히든 크기 | 4,096 | 각 토큰을 표현하는 벡터의 차원 |
| FFN 크기 | 14,336 | Feed-Forward 중간 크기 |
| 어텐션 헤드 | 32개 | 동시에 주목하는 "관점" 수 |
| 시퀀스 길이 | 8,192 토큰 | 한 번에 처리하는 텍스트 길이 |
| 어휘 크기 | 128,256 | 모델이 아는 단어(토큰) 수 |

### Self-Attention: "어떤 단어를 주목할까?"

Self-Attention은 문장에서 관련 있는 단어끼리 연결해주는 메커니즘입니다.

```
"고양이가 매트 위에 앉았다. 그것은 편안해 보였다."

Q: "그것" 이 무엇을 가리키는지 알기 위해...
                    ↓
   [고양이가] [매트] [위에] [앉았다] [그것은] [편안해] [보였다]
      0.7      0.1   0.0    0.1      -       0.05    0.05
                    ↓
   "그것" = "고양이" (Attention Score 0.7로 가장 높음)
```

**수학적으로:**

```
Attention(Q, K, V) = softmax(Q × K^T / √d) × V

Q (Query):  "나는 무엇을 찾고 있는가?"  (질문)
K (Key):    "나는 어떤 정보를 가지고 있는가?"  (열쇠)
V (Value):  "내가 전달할 실제 정보"  (값)
d = 128:    헤드 차원 (스케일링 계수)
```

이 연산이 32개 "헤드"에서 병렬로 일어나고, 이를 32개 레이어에서 반복합니다.

## 5. 학습의 원리: 경사 하강법

### 비유: 안개 낀 산에서 골짜기 찾기

모델 학습은 **"안개 낀 산에서 가장 낮은 골짜기를 찾는 것"** 과 같습니다.

```
Loss (높이)
  │
  │  ●  ← 시작점 (loss=9.26, 아무것도 모르는 상태)
  │   \
  │    \     /\
  │     \   /  \
  │      \_/    \      /\
  │              \    /  \
  │               \__/    \___●  ← 목표 (loss≈3.3)
  │
  └─────────────────────────────→  학습 스텝
     0    5000   10000  15000  20000
```

- **현재 위치** = 모델의 파라미터 값들 (80억 개의 숫자)
- **높이** = Loss (예측 오차). 낮을수록 좋음
- **기울기 (Gradient)** = "어느 방향으로 가면 내려갈 수 있는가?"
- **한 걸음** = 파라미터를 기울기 반대 방향으로 조금 수정

### 수학적 표현

```
θ(t+1) = θ(t) - lr × ∇L(θ(t))

θ:    파라미터 (80억 개의 숫자)
lr:   Learning Rate (보폭 크기)
∇L:   Loss의 기울기 (어느 방향이 내리막인지)
t:    현재 스텝 번호
```

### AdamW 옵티마이저: 똑똑한 등산가

단순 경사 하강법 대신 **AdamW** 라는 고급 방법을 사용합니다.
이것은 마치 "경험 많은 등산가"와 같습니다:

```
┌──────────────────────────────────────────────────────┐
│  AdamW의 세 가지 지혜                                  │
│                                                       │
│  1. 모멘텀 (β1=0.9): "관성을 이용하자"                  │
│     → 이전에 내려가던 방향을 기억해서 흔들림 감소          │
│     → 작은 웅덩이에 빠지지 않고 큰 골짜기로 향함          │
│                                                       │
│  2. 적응적 학습률 (β2=0.95): "지형에 맞게 보폭 조절"     │
│     → 가파른 곳에서는 작은 보폭, 완만한 곳에서는 큰 보폭  │
│     → 각 파라미터마다 다른 보폭 사용                     │
│                                                       │
│  3. Weight Decay (0.1): "너무 멀리 가지 않기"            │
│     → 파라미터가 너무 큰 값을 갖지 않도록 규제            │
│     → 과적합(외우기) 방지                               │
└──────────────────────────────────────────────────────┘
```

**AdamW 파라미터 설정:**

| 파라미터 | 값 | 의미 |
|---------|-----|------|
| β1 | 0.9 | 모멘텀 계수 (과거 기울기 방향 90% 유지) |
| β2 | 0.95 | 분산 계수 (기울기 크기의 이동 평균) |
| ε | 1e-5 | 0으로 나누기 방지용 아주 작은 수 |
| Weight Decay | 0.1 | 파라미터 크기 규제 강도 |
| Gradient Clip | 1.0 | 기울기가 폭발하지 않도록 최대값 제한 |

## 6. Learning Rate: 학습의 보폭

### Learning Rate란?

Learning Rate(LR)는 **"한 번에 얼마나 크게 수정할 것인가"** 를 결정합니다.

```
LR이 너무 작으면 (0.00005):          LR이 적절하면 (0.0004):        LR이 너무 크면 (0.01):

  Loss                               Loss                          Loss
  │●                                 │●                            │●
  │ ●                                │ \                            │ \    /●
  │  ●                               │  \                           │  \  /
  │   ●                              │   \                          │   \/
  │    ●●                            │    \_                        │      \  /
  │      ●●                          │      \__                     │       \/
  │        ●●●                       │         \___●               │
  │           ●●●●                   │                              │  → 발산!
  └──────────→                       └──────────→                   └──────────→
  너무 느림! (스텝 많이 필요)          적절! (빠르게 수렴)              불안정! (발산 위험)
```

### Learning Rate Schedule: 코사인 감쇄

학습 내내 같은 LR을 사용하지 않고, 시간에 따라 변화시킵니다:

```
LR
│
│     ╱‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾╲
│    ╱                   ╲
│   ╱                     ╲
│  ╱                       ╲
│ ╱                         ╲
│╱                           ╲
│                              ╲_______________
└──────────────────────────────────────────────→ 스텝
  ↑                    ↑                     ↑
 Warmup              Peak LR              Min LR
 (128 스텝)        (LR=0.0004)        (LR/10=0.00004)
```

**3단계 과정:**

1. **Warmup (0~128 스텝)**: LR을 0에서 서서히 올림
   - 학습 초기에 갑자기 큰 보폭으로 이동하면 불안정
   - 천천히 보폭을 늘려가며 안정적으로 출발

2. **Peak → Decay (128~끝)**: 코사인 곡선을 따라 서서히 감소
   - 처음에는 대략적인 방향을 잡아야 하므로 큰 보폭
   - 점점 정밀하게 조정해야 하므로 보폭을 줄임

3. **Min LR**: 최소 학습률 = Peak의 1/10
   - 완전히 0으로 내리지 않고 약간의 탐색 유지

### 우리의 LR 실험 결과

```
┌──────────────┬──────────────┬──────────────┬─────────────────┐
│   LR 값      │  수렴 스텝    │  총 시간      │  결과            │
├──────────────┼──────────────┼──────────────┼─────────────────┤
│ 0.00015      │   24,192     │  48.3시간     │ 성공 (기본값)     │
│ (기본)       │              │              │                  │
├──────────────┼──────────────┼──────────────┼─────────────────┤
│ 0.0003       │   23,040     │  42.8시간     │ 성공 (-11.4%)    │
│              │  (4.8%↓)     │              │                  │
├──────────────┼──────────────┼──────────────┼─────────────────┤
│ 0.0004       │   20,352     │  37.9시간     │ 성공 (-21.5%)    │
│ (현재 최적)   │  (15.9%↓)   │              │                  │
├──────────────┼──────────────┼──────────────┼─────────────────┤
│ 0.0005       │      ?       │      ?       │ 테스트 예정       │
│              │              │              │  (발산 위험 있음)  │
└──────────────┴──────────────┴──────────────┴─────────────────┘
```

### 왜 높은 LR이 더 빠를까?

```
낮은 LR (보폭 작음):              높은 LR (보폭 큼):

●→●→●→●→●→●→●→●→●→●→●→●→●→골   ●──→●──→●──→●──→●──→골
  1  2  3  4  5  ...  24192         1    2    3   ... 20352

같은 거리를 가는데                   큰 보폭으로
작은 걸음으로 더 많이 걸어야 함         적은 걸음으로 도착
```

**하지만 주의사항:**
- 보폭이 너무 크면 골짜기를 건너뛰어서 **발산** (loss가 증가)
- 적절한 LR은 모델, 데이터, 배치 크기에 따라 달라짐
- 실험을 통해 최적값을 찾아야 함

## 7. 배치 사이즈와 메모리의 관계

### 배치 사이즈의 계층 구조

```
┌─────────────────────────────────────────────────────────┐
│  Global Batch Size (GBS) = 8                             │
│  "한 스텝에서 모델이 학습하는 총 텍스트 수"                  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐    │
│  │  Mini Batch Size (MINIBS) = 8                     │    │
│  │  "한 GPU 그룹이 처리하는 텍스트 수"                │    │
│  │                                                    │    │
│  │  ┌─────────────────────────────────────────┐      │    │
│  │  │  Micro Batch Size (MBS) = 1              │      │    │
│  │  │  "한 번의 forward pass에 처리하는 수"      │      │    │
│  │  └─────────────────────────────────────────┘      │    │
│  │        × 8번 반복 (Gradient Accumulation)          │    │
│  └──────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

### Gradient Accumulation: 적은 메모리로 큰 배치 효과

GPU 메모리에 한 번에 텍스트 1개만 올릴 수 있지만,
기울기를 8번 누적하면 텍스트 8개를 한꺼번에 본 것과 같은 효과를 냅니다.

```
스텝 1번의 진행:

  MBS 1: Forward → Loss → Backward → 기울기 저장
  MBS 2: Forward → Loss → Backward → 기울기 누적 (+)
  MBS 3: Forward → Loss → Backward → 기울기 누적 (+)
  ...
  MBS 8: Forward → Loss → Backward → 기울기 누적 (+)

  → 8번의 기울기 평균으로 파라미터 업데이트 (1 스텝 완료)
```

**메모리 vs 속도 트레이드오프:**

| MBS | GPU 메모리 사용 | GA 횟수 | 스텝 시간 |
|-----|--------------|---------|----------|
| 1 | 낮음 (~90GB) | 8 | ~5.9초 |
| 2 | 높음 (~93GB+) | 4 | OOM 위험 |

MBS=1이 안전하지만, MBS=2가 되면 커널 실행 오버헤드가 절반으로 줄어 더 빠릅니다.
다만 우리 환경에서는 메모리 여유가 부족해서 MBS=1을 사용합니다.

## 8. 병렬 처리: 하나의 모델을 여러 GPU에 나누기

### 왜 병렬 처리가 필요한가?

80억 개 파라미터를 BF16으로 저장하면 약 16GB입니다.
하지만 학습에 필요한 옵티마이저 상태, 기울기, 활성화 값까지 합치면
**하나의 GPU 93GB로는 부족**합니다.

### Tensor Parallelism (TP=2): 행렬을 반으로 쪼개기

우리 설정의 핵심 병렬화 방식입니다.

```
                    TP 없이 (1 GPU):

                    GPU 0
                    ┌──────────────┐
                    │  W (전체)     │
                    │  [4096×14336] │  ← 234MB
                    └──────────────┘

                    TP=2 (2 GPU에 분할):

        GPU 0                          GPU 1
        ┌──────────────┐              ┌──────────────┐
        │  W의 왼쪽 절반  │              │  W의 오른쪽 절반 │
        │  [4096×7168]  │    ◄─────►  │  [4096×7168]  │
        └──────────────┘   통신(동기화)  └──────────────┘
                              117MB씩
```

**작동 방식:**
1. 각 GPU가 가중치 행렬의 절반만 저장
2. Forward: 각 GPU가 자기 부분만 계산
3. 결과를 AllReduce로 합침 (GPU 간 통신 발생)
4. Backward: 마찬가지로 분할 계산 + 통신

**장점:** 메모리 사용량이 절반으로 줄어듬
**단점:** GPU 간 통신 오버헤드 (PCIe 환경에서 특히 비용이 큼)

### 다른 병렬화 방식들 (현재 비활성화)

```
┌──────────────────────────────────────────────────────────────────┐
│                    병렬화 방식 종합                                 │
│                                                                   │
│  TP (Tensor Parallel) = 2     ✅ 사용 중                          │
│  → 하나의 레이어 안에서 행렬을 GPU에 분할                            │
│  → 매 레이어마다 GPU 간 통신 필요                                   │
│                                                                   │
│  PP (Pipeline Parallel) = 1   ❌ 비활성                            │
│  → 레이어를 GPU에 순차 배치 (GPU0=레이어1-16, GPU1=레이어17-32)      │
│  → 파이프라인 버블로 효율 감소, GPU가 2개뿐이라 부적합                 │
│                                                                   │
│  DP (Data Parallel) = 1       ❌ 자동 비활성                        │
│  → 같은 모델을 여러 GPU에 복제, 다른 데이터로 학습                    │
│  → DP = 총 GPU수 / (TP × PP × CP) = 2 / (2×1×1) = 1             │
│  → GPU가 2개뿐이고 TP=2라서 DP는 자동으로 1                         │
│                                                                   │
│  CP (Context Parallel) = 1    ❌ 비활성                            │
│  → 긴 시퀀스를 GPU에 분할                                          │
│  → 시퀀스 8192는 충분히 짧아서 불필요                                │
│                                                                   │
│  SP (Sequence Parallel) = False  ❌ 비활성                          │
│  → LayerNorm, Dropout을 시퀀스 차원으로 분할                        │
│  → TP와 함께 사용 시 메모리 절약 가능                                │
└──────────────────────────────────────────────────────────────────┘
```

### 한 스텝의 시간 분석 (~5.9초)

```
5.9초 = 이렇게 나뉩니다 (대략적)

┌─────────────────────────────────────────────────────────┐
│ Forward Pass (약 40%)        │ ~2.4초                    │
│ → 32 레이어 순차 통과          │                          │
│ → Self-Attention + FFN        │                          │
├─────────────────────────────────────────────────────────┤
│ Backward Pass (약 45%)       │ ~2.6초                    │
│ → 기울기 역전파                │                          │
│ → GPU 간 기울기 AllReduce      │                          │
├─────────────────────────────────────────────────────────┤
│ 옵티마이저 + 기타 (약 15%)    │ ~0.9초                    │
│ → AdamW 파라미터 업데이트      │                          │
│ → 데이터 로딩 (오버랩)         │                          │
│ → GPU 간 파라미터 동기화       │                          │
└─────────────────────────────────────────────────────────┘

× 8 (Gradient Accumulation)
= 한 스텝에 Forward+Backward가 8번 실행
```

## 11. 수렴 판정: 학습이 성공했는지 어떻게 아는가?

### Log Perplexity (log_ppl)

**Perplexity**는 "모델이 다음 단어를 예측할 때 얼마나 헷갈려하는가"를 측정합니다.

```
Perplexity = e^(loss)
Log Perplexity = loss (자연로그 기준)

예시:
- log_ppl = 9.0  →  e^9 = 8,103    "8,103개 단어 중 하나를 고르는 수준" (매우 못함)
- log_ppl = 5.0  →  e^5 = 148      "148개 단어 중 고르는 수준" (보통)
- log_ppl = 3.3  →  e^3.3 = 27     "27개 단어 중 고르는 수준" (졸업!)
- log_ppl = 2.0  →  e^2 = 7.4      "7개 단어 중 고르는 수준" (매우 잘함)
```

### 검증 과정

```
매 384 스텝마다:

1. 학습 일시 중지
2. 검증 데이터 1,024개 샘플 로드 (학습에 사용하지 않은 데이터)
3. 모델이 검증 데이터의 다음 단어를 예측 (기울기 계산 없이)
4. 평균 Loss 계산 = log_ppl
5. log_ppl ≤ 3.3이면 → "졸업!" (학습 성공 종료)
6. 아니면 → 학습 계속

검증 1회 소요 시간: 약 48초
(128 batches × 0.376초/batch)
```

### 수렴 곡선 (실제 데이터 기반)

```
log_ppl
  10 │●
     │ \
   8 │  \
     │   \
   6 │    \
     │     \
   5 │      \
     │       \
   4 │        \___
     │            \____
 3.3 │─ ─ ─ ─ ─ ─ ─ ─ ─\─ ─ ─ ─  목표선
   3 │                    \●
     │
   2 │
     └─────────────────────────→ 스텝
     0    5K   10K   15K   20K

     LR=0.0004 기준: 약 20,352 스텝에서 수렴
```

## 12. 최적화 실험 기록과 분석

### 전체 실험 히스토리

우리는 다양한 최적화를 시도했고, 각각의 결과를 기록했습니다:

```
실험 번호    설정                          결과           Step Time    비고
─────────────────────────────────────────────────────────────────────────
Job 170     Baseline (TE=False, LR=0.00015)  성공 24,192스텝  6.35s    기준선
Job 167     TE=True + NCCL 버퍼 축소         성공 500스텝     5.50s    13% 빠름
Job 168     TE=True, CE=te (풀런)            실패            5.50s    log_ppl 4.66에서 정체
Job 169     TE=True, CE=native (풀런)        실패            5.50s    log_ppl 4.23에서 정체
Job 171     Flash Attention (TE=False)        -              6.40s    오히려 느림
Job 173     LR=0.0003 (풀런)                 성공 23,040스텝  5.89s    4.8% 스텝 감소
Job 175     LR=0.0004 (풀런)                 성공 20,352스텝  5.88s    15.9% 스텝 감소
```

### 시도한 최적화와 원리

#### (1) Transformer Engine (TE) — 속도 향상 but 수렴 실패

**TE란?**: NVIDIA가 만든 라이브러리로, 여러 연산을 하나로 합쳐서(fused) GPU 효율을 높입니다.

```
TE 없이 (개별 연산):                    TE 있을 때 (Fused 연산):

GPU 메모리                              GPU 메모리
  ↓ 읽기                                  ↓ 읽기 (1번만)
LayerNorm 계산                          LayerNorm + Attention + Dropout
  ↓ 쓰기                                  ↓ 쓰기 (1번만)
  ↓ 읽기
Attention 계산                          → 메모리 읽기/쓰기 횟수가
  ↓ 쓰기                                  크게 줄어서 빠름!
  ↓ 읽기
Dropout 적용
  ↓ 쓰기

총 6번의 메모리 접근                      총 2번의 메모리 접근
```

**결과**: 스텝당 속도는 6.35s → 5.50s (13% 향상)이었지만,
TE의 수치 연산 방식이 미묘하게 달라 **학습이 수렴하지 않았습니다**.

이는 fused 커널이 연산 순서나 부동소수점 반올림을 다르게 처리하여
80억 개 파라미터의 업데이트가 미세하게 달라지고,
이 차이가 수만 스텝에 걸쳐 누적되어 수렴 실패로 이어진 것입니다.

#### (2) Flash Attention — H100에서는 불필요

**Flash Attention이란?**: Attention 연산을 메모리 효율적으로 재구성한 알고리즘

```
일반 Attention:                         Flash Attention:
Q×K^T 전체를 먼저 계산                    Q×K^T를 블록 단위로 계산
→ [8192×8192] 행렬 생성 (512MB)          → 전체 행렬을 메모리에 안 올림
→ Softmax 적용                          → 블록별로 Softmax
→ ×V 곱하기                             → 블록별로 ×V
                                         → 메모리 절약!
```

**결과**: H100 GPU는 이미 cuDNN의 최적화된 fused attention을 기본 사용하므로,
별도의 Flash Attention이 오히려 느렸습니다 (6.35s → 6.40s).

#### (3) Learning Rate 증가 — 가장 효과적인 최적화

**원리**: 보폭을 키워서 같은 목표에 더 적은 걸음으로 도달

```
LR=0.00015 경로:    ●→●→●→●→●→●→●→●→●→ ... →●→●→●  (24,192 스텝)
LR=0.0003  경로:    ●──→●──→●──→●──→● ... ──→●──→●  (23,040 스텝)
LR=0.0004  경로:    ●───→●───→●───→● ... ───→●       (20,352 스텝)
```

**핵심**: 모델 구조나 하드웨어를 건드리지 않고,
순수하게 "학습 전략"만 바꿔서 **15.9% 스텝 감소**를 달성했습니다.

#### (4) NCCL 버퍼 축소 — 57MB의 마법

TE 활성화 시 OOM이 발생했던 원인과 해결:

```
OOM 상황:
  GPU 전체: 93,090 MB
  PyTorch:  90,360 MB (사용 중)
  필요:      1,002 MB (logits 텐서)
  가용:        946 MB
  부족:         56 MB  ← 겨우 56MB 부족!

해결:
  NCCL_MAX_NCHANNELS=2    (16→2, 채널 수 줄임)
  NCCL_BUFFSIZE=1048576   (4MB→1MB, 버퍼 크기 줄임)
  → 약 60MB 절약 → OOM 해결!
```

NCCL은 GPU 간 통신을 위해 GPU 메모리에 버퍼를 할당합니다.
이 버퍼를 줄이면 통신 효율이 약간 떨어지지만,
PCIe 환경에서는 이미 대역폭이 병목이라 체감 차이가 미미합니다.

## 14. 용어 사전

| 용어 | 영문 | 설명 |
